# 01 — 路线 C 滑块链路：拓扑 / 部署 / 排障

## 1. 为什么叫「路线 C」

滑块验证在闲鱼侧是阿里 nc（NoCaptcha）的「拖到底」型验证码：把滑块拖到最右端。
上游方案是**在容器里跑有头 Chromium，用 CDP 派发鼠标事件自动拖**。
本机实测这条路通过率 **0** —— 阿里 nc 会比对输入事件的时间分布：

- CDP `Input.dispatchMouseEvent` 派发的是「**每帧一个**」合成事件；
- 真机鼠标是「**一帧多个子采样**」，且走 `user32!SendInput` 的 OS 输入栈。

因此改成**路线 C**：由一台真实 Windows 机器上的 Chrome 渲染页面，
用一个常驻的 HTTP 执行器（`driver.ps1`）调 `user32!SendInput` 做真实拖动。
实测完整闭环成功率约 **77%~83%**。

## 2. 拓扑

```
┌──────────────────────────┐
│ <VM102_IP>  应用机        │
│  docker: xianyu-super-butler
│   ├─ 面板/后端 :8080      │
│   │   └─ utils/slider_route_c.py      客户端（熔断 + 重试序列）
│   └─ routec-solver :8799  ← 容器内，127.0.0.1
│        ├─ slider_routec/preflight.py  六项体检 + 自愈
│        ├─ slider_routec/routec_core.py 单轮编排
│        ├─ slider_routec/driverctl.py   HTTP 调真机执行器
│        └─ slider_routec/humanize.py    人类化轨迹生成
└───────────┬──────────────┘
            │ TCP（直连隧道落点：<VM102_IP>:8791 / :9222）
            │
            │ 反向 SSH 隧道（真机主动连出，落点就是上面这台应用机）
┌───────────▼──────────────┐
│ <VM101_IP>  Windows 真机  │
│  driver.ps1  :8791        ← 交互会话（Session 1），SendInput
│  Chrome      :9222 (CDP)  ← --remote-debugging-port
└──────────────────────────┘
```

**没有中转机器这一跳**：真机的 `revtunnel.cmd` 直接 `ssh -R` 把 `8791` / `9222` 反连到
应用机 `<VM102_IP>`，容器直连 `<VM102_IP>:8791` / `:9222`。（历史文档里的 `<VM100_IP>`
中转已废弃；若那台机器还在，它服务的是 `reverse_agent` 的抓包隧道，与本应用无关。）

前提：应用机 sshd `GatewayPorts clientspecified`，否则 `-R` 只绑 `127.0.0.1`，
bridge 网络里的容器连接会被拒（真机侧看隧道是「建好了」的，极具迷惑性）。

### 关键进程与端口

| 位置 | 端口 | 是什么 |
| --- | --- | --- |
| 容器内 | `127.0.0.1:8799` | `routec-solver`，由 `entrypoint.sh` 后台拉起 |
| `<VM102_IP>`（应用机 / 隧道落点） | `8791` | 真机执行器（driver.ps1）的反向隧道落点 |
| `<VM102_IP>`（应用机 / 隧道落点） | `9222` | 真机 Chrome CDP 的反向隧道落点 |
| 真机 | `127.0.0.1:8791` | `driver.ps1` 的 HTTP 服务 |
| 真机 | `127.0.0.1:9222` | Chrome `--remote-debugging-port` |

鉴权：求解器的 `/solve`、`/health` 用请求头 `X-RouteC-Token`（值 = `.env` 的
`SLIDER_ROUTE_C_TOKEN` = 镜像内 `custom/slider_routec/token`）。容器内 `127.0.0.1` 调用也要带。

## 3. 一次求解的完整流程

```
POST /solve (X-RouteC-Token)
  │
  ├─ 1) preflight.check_and_heal(timeout≤90s)   ← 六项体检，见 §4
  │      失败 → reason="preflight"，**不发起任何闲鱼请求**（不消耗账号）
  │
  ├─ 2) 整账号 cookie 交换：注入账号 cookie，清掉挑战痕迹
  │      （x5secdata / x5sectag / x5step / x5sec），逼出**新鲜**挑战
  │
  ├─ 3) 打开 punish 页面，等挑战出现
  │
  ├─ 4) screen↔client 校准：SendInput 把鼠标移到固定点，读页面 window.__lastMM
  │      （校准点见 §6 的坑 4/5）
  │
  ├─ 5) humanize 生成轨迹 → driver `drag`（分步 + 子采样 SendInput）
  │
  ├─ 6) 等响应 cookie 出现 x5sec（通行凭证）
  │
  └─ 7) 闭环校验（可选，`SLIDER_ROUTE_C.verify`）
       用 x5sec + 账号 cookie 重试一次业务请求
```

返回体（**不含任何凭据**）：

```json
{"ok": true, "reason": "pass", "x5sec": "...", "x5_cookies": {...},
 "elapsed_s": 37.7, "moves": 264, "preflight": {"ok": true, "blocked_at": null, ...}}
```

## 4. 六项前置体检（preflight）

`slider_routec/preflight.py` 的 `check_and_heal(timeout_s) -> dict`，按序执行，
任一项不可恢复即返回 `ok=false` / `blocked_at=<step>`：

| # | id | 检查 | 自愈 |
| --- | --- | --- | --- |
| 1 | `driver` | `ROUTEC_DRIVER_URL` 可达（`probe`） | 无；失败即中止 |
| 2 | `lock` | 真机是否锁屏（`state.locked`） | `unlock`（未锁 → noop；锁屏 → 读密码文件注入）；仍锁 → 中止 |
| 3 | `chrome` | Chrome 进程数（`state.chrome`） | `launch-chrome` + 轮询 CDP ≤45s |
| 4 | `cdp` | `{CDP_URL}/json/version` | 同 3 |
| 5 | `window` | Chrome **主**窗口是否最小化 / 未置前 | `focus`（`SW_RESTORE` + `SetForegroundWindow`） |
| 6 | `page` | CDP 里有 goofish target | 无（求解器会新建），仅记录 |

硬约束：整体预算上限 `OVERALL_MAX_S = 90s`；单步 driver 调用 8s；`unlock` 30s。

`/health` = 「六项全过才 200，否则 503」。

## 5. 部署清单

### 5.1 应用机（`<VM102_IP>`）

1. `cp .env.example .env`，填 `SLIDER_ROUTE_C_TOKEN`（`openssl rand -hex 24`）。
2. 同一个值写进 `custom/slider_routec/token`（`chmod 600`）。
3. `cd custom && docker build -f Dockerfile.overlay -t xianyu-super-butler:custom .`
4. `docker compose up -d`。

### 5.2 反向隧道（真机 → 应用机，**本应用不需要中转机器**）

真机侧用 `ssh -R` 把 `8791` / `9222` 反连到**应用机** `<VM102_IP>`：

```
<VM101_IP>  ──revtunnel.cmd（ssh -R 8791:127.0.0.1:8791 -R 9222:127.0.0.1:9222）──▶  <VM102_IP>
```

**两个必须注意的点**（都是实测踩出来的）：

1. **`GatewayPorts clientspecified`**：应用机 `<VM102_IP>` 的 sshd 若保持默认 `no`，
   `-R` 只把端口绑到 `127.0.0.1`。容器在 bridge 网络里，访问 `127.0.0.1:8791` 是**容器自己**，
   不是宿主 —— 连接被拒、但隧道本身「看起来是好的」。改法：`/etc/ssh/sshd_config.d/*.conf`
   加 `GatewayPorts clientspecified` + `systemctl reload ssh`。
2. **同一端口别开两条隧道**：`ExitOnForwardFailure=yes` 时后到的那条会直接退出。

> 真机执行器能注入键盘鼠标 —— 反向隧道落点所在机器要按「信任边界」对待，
> 别把 `8791` 暴露到不受控网段。

### 5.3 真机（`<VM101_IP>`）

见 [`../custom/vm101/README.md`](../custom/vm101/README.md)。

## 6. 排障：四个「假活」坑

这四个都是**看起来正常、实际不通**的假象，最容易浪费时间。判活一律用**端到端真实调用**，
不要看进程/任务状态。

### 坑 1：计划任务状态恒为 `Ready`，但驱动其实在跑

`driver.ps1` 由 `run-hidden.vbs`（`WScript.Shell.Run(..., 0, False)`）**非阻塞**拉起，
所以计划任务 `WinInputDriver` 的状态会一直停在 `Ready` —— **不代表驱动没跑**。

- ❌ 不要用 `schtasks /Query /TN WinInputDriver` 的状态判活
- ✅ 用 `POST http://<VM102_IP>:8791/ {"action":"probe"}`，`ok:true` 才算活着

### 坑 2：`chromeWindow` 的假阳性（类名匹配）

Windows 上 **Electron 应用（如各种 AI 桌面端）也注册 `Chrome_WidgetWin_1` 窗口类**。
只按类名匹配 → Chrome 明明没运行，`chromeWindow` 也是 `true`。

- ❌ `chromeClassWindow`（纯类名匹配）不能用来判「Chrome 是否真的起来」
- ✅ 用 `chromeWindow`（语义 = 存在**属于 `chrome.exe` 进程**的可见 `Chrome_WidgetWin_1` 窗口）
  和 `chromeIconic`（该窗口是否最小化）
- `focus` 调用建议带上 `{"class":"Chrome_WidgetWin_1","exe":"chrome"}`，否则可能把
  Electron 应用的窗口置前

### 坑 3：端口在听 ≠ 链路通

实测遇到过：`<VM102_IP>`（隧道落点）上 `127.0.0.1:9222` 确实在 `LISTEN`，但持有它的
`sshd-session` 的**转发线程已经死了** —— 端口还在，转发不通。

- ❌ 不要用 `ss -lntp | grep 9222` 判断链路可用
- ✅ 用 `curl http://<VM102_IP>:9222/json/version` 拿到 200 才算通
- 判 `8791` 同理：`POST / {"action":"probe"}`
- 另一种「端口在听但不通」是 sshd 的 `GatewayPorts` 没开（见 §5.2 坑 1）：此时端口绑在
  `127.0.0.1` 上，从**别的网络命名空间**（容器）连过去会被拒

### 坑 4：窗口存在 ≠ 能收到鼠标（未置前 / 被遮挡）

拖动前要用 `SendInput` 把鼠标移到校准点做 screen↔client 校准。
**如果 Chrome 不是前台窗口**（被别的窗口盖住），鼠标事件到不了页面，校准必然失败：

```
校准失败：未观测到鼠标事件
```

- ✅ preflight 第 5 项把「最小化 **或** 未置前」都纳入检查，调 `focus` 还原 + 置前
- ✅ 挑窗口时优先标题含 `Google Chrome` 的（Chrome 主窗口标题恒为 `<页面> - Google Chrome`），
  避开 Chrome 自己弹的同 class 小窗（例如崩溃恢复气泡「要恢复页面吗？」）

### 附：第 5 个真 bug —— 校准点死循环

首次实现里，校准点固定为 `(600,500)`。若**光标本来就在** `(600,500)`，
Windows 对「位置未变」的移动**不派发 `WM_MOUSEMOVE`** → 读回 `null` → 校准失败；
而失败又把光标留在校准点 → **之后每一轮都必然失败**，整条链路永久卡死。

修法：首次读不到就「**先挪开再回来**」，逼出一次真实移动，再读一次。

```
同位置单次 move 后      __lastMM = None
抖动 (620,520)->(600,500) 后 __lastMM = {'x': 592, 'y': 413}
```

## 7. 常用排查命令

```bash
# 1) 容器内体检（最快看到卡在哪一步）
docker exec xianyu-super-butler python /app/slider_routec/preflight.py --timeout 60

# 2) 求解器健康
docker exec xianyu-super-butler sh -c 'curl -s http://127.0.0.1:8799/health'

# 3) 直接打真机执行器（从 <VM102_IP> 直连隧道落点）
curl -s -X POST http://<VM102_IP>:8791/ -d '{"action":"state"}'

# 4) 直接打 CDP
curl -s http://<VM102_IP>:9222/json/version

# 5) 求解器日志（启动日志 + 每轮结果）
docker exec xianyu-super-butler tail -n 100 /app/logs/routec-solver-boot.log
docker logs xianyu-super-butler | grep -E 'preflight|滑块验证'
```

`/solve` 的响应体与日志都带 `preflight` 字段 —— 失败时先看 `preflight.blocked_at`
就能定位到具体哪一环。

## 8. 环境变量一览

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `SLIDER_ROUTE_C_TOKEN` | — | 求解器鉴权令牌（必填，与 `slider_routec/token` 一致） |
| `SLIDER_ROUTE_C_ENABLED` | `true` | 总开关 |
| `SLIDER_ROUTE_C_ENDPOINT` | `http://127.0.0.1:8799` | 求解器地址 |
| `SLIDER_ROUTE_C_MAX_ATTEMPTS` | `5` | 一次求解序列最多几轮 |
| `ROUTEC_DRIVER_URL` | `http://<VM102_IP>:8791/` | 真机执行器（反向隧道落点在应用机） |
| `ROUTEC_CDP_URL` | `http://<VM102_IP>:9222` | 真机 Chrome CDP（同上） |

> 这两个变量在 `custom/slider_routec/preflight.py` 里有**占位符默认值**，
> 实际部署时用 `.env` / `docker-compose.yml` 的环境变量覆盖（`docker-compose.example.yml`
> 的 `environment:` 段已留位置）。指向**应用机自己**即可 —— 容器直连隧道落点，不需要任何中转机器。
