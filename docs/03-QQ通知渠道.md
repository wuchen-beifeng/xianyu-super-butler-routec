# 03 — QQ 通知渠道（NapCat / OneBot v11）

## 1. 上游有什么、缺什么

上游「通知渠道」支持的类型：`dingtalk` / `feishu` / `bark` / `email` / `webhook` / `wechat` / `telegram`。
**没有 QQ**。

本仓库新增 `qq` 类型，实现为 **OneBot v11 私聊**，兼容 NapCat（`napcat` / `onebot` 作为别名）。

---

## 2. 协议契约（重要）

```
POST {base_url}/send_private_msg
Headers: Authorization: Bearer <access_token>      # access_token 非空才带
Body:    {"user_id": <int>, "message": "<text>"}
```

**成功判据 = 响应体 `retcode == 0`。**

HTTP 200 **不算成功** —— NapCat / OneBot 用「HTTP 200 + `retcode != 0`」表达业务失败
（比如目标不是好友、token 不对）。所以：

- 必须能解析出 `retcode`（`code` / `errcode` 也认），拿不到同样按失败处理；
- `retcode != 0` → 抛 `NotificationProviderRejected`，进渠道失败统计。

`base_url` 是**服务根地址**，不带 `/send_private_msg`，例如 `http://<NAS_IP>:3000`。

---

## 3. 配置

### 3.1 面板（推荐）

「通知」页 → 新增渠道 → 类型选 **`QQ（NapCat/OneBot）`**：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `base_url` | ✅ | NapCat 的 HTTP 服务地址，如 `http://<NAS_IP>:3000` |
| `user_id` | ✅ | 接收通知的 QQ 号（**正整数**；非数字会被拒绝，避免静默发错人） |
| `access_token` | ❌ | NapCat 配了 token 就填；会以 `Authorization: Bearer <token>` 发出 |

保存后点「测试」发一条验证。

### 3.2 NapCat 侧

1. 开启 NapCat 的 **HTTP 服务**（HTTP Server），记下端口（默认常见 `3000`）。
2. 如果配了 token，填进渠道的 `access_token`。
3. 用 `curl` 先验证一次：

```bash
curl -s -X POST http://<NAS_IP>:3000/send_private_msg \
  -H 'Authorization: Bearer <你的token>' \
  -H 'Content-Type: application/json' \
  -d '{"user_id": <QQ号>, "message": "hello"}'
# 期望：{"status":"ok","retcode":0,...}
```

`retcode` 不是 0 → 先修 NapCat 侧（token / 好友关系 / 端口），再看面板。

## 4. 什么时候会发 QQ

走既有的事件体系，不新增事件：

| 触发 | 事件 | 映射 |
| --- | --- | --- |
| 滑块重试序列耗尽（路线 C 是唯一路径，无回退） | `captcha_route_c_exhausted` | → `captcha_manual` |
| 其他滑块相关失败 | `captcha_max_retries_exceeded` / `captcha_manual_required` / `captcha_verification_failed` / `captcha_dependency_missing` / `captcha_execution_error` | → `captcha_manual` |
| 人脸验证 | `face_verification` | → `captcha_manual` |

`captcha_manual` = 「人工验证提醒」，级别 **critical**，描述「滑块、人脸或扫码验证需要人工处理」。

**注意**：上游在「WebSocket 已连接」时会跳过通知。本仓库已去掉这个短路 ——
路线 C 重试耗尽就是**终态**，必须通知到人，不能因为面板开着就不发。

## 5. 代码位置

| 文件 | 内容 |
| --- | --- |
| `app/services/notification_channels.py` | `NOTIFICATION_CHANNEL_REQUIRED_FIELDS["qq"] = ("base_url", "user_id")`；别名 `napcat` / `onebot` → `qq`；`user_id` 归一化为正整数 |
| `app/services/notification_sender.py` | `NotificationSender._send_qq()`（`_send_qq` 注册进 `CHANNEL_SENDERS["qq"]`） |
| `app/notification_events.py` | `TOKEN_NOTIFICATION_EVENT_MAP["captcha_route_c_exhausted"] = "captcha_manual"` |
| `XianyuAutoAsync.py` | `_send_qq_notification()`；`match channel_type` 增加 `case 'qq' \| 'napcat' \| 'onebot'` |
| `frontend/components/NotificationsAndLogs.tsx` | 渠道类型下拉新增 `qq`，三个字段 |

构建期硬断言（`Dockerfile.overlay` 的 T5 段）会校验：

```
NOTIFICATION_CHANNEL_REQUIRED_FIELDS['qq'] == ('base_url', 'user_id')
normalize_channel_type('napcat') == 'qq'
NotificationSender 有 _send_qq
TOKEN_NOTIFICATION_EVENT_MAP['captcha_route_c_exhausted'] == 'captcha_manual'
XianyuAutoAsync.py 里有 def _send_qq_notification 和 case 'qq'
```

任一不满足，镜像构建直接失败。

---

## 6. 排障

| 现象 | 原因 / 处置 |
| --- | --- |
| 面板测试报「配置缺少字段」 | `base_url` / `user_id` 为空，或 `user_id` 不是数字 |
| 测试返回失败但 NapCat 日志显示已发送 | 多半是 `retcode != 0`（非好友 / 被限制）—— 本仓库按失败处理是**故意的** |
| `docker logs` 里 `不支持的通知渠道类型: qq` | 跑的是旧镜像（不含 T5 的 `case 'qq'` 分支），重新叠加构建 |
| 滑块失败但没收到 QQ | ① 渠道没启用；② 事件没映射到 `captcha_manual`；③ NapCat HTTP 服务没开 |
